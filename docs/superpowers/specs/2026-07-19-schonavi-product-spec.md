# SchoNavi 产品规格：对话内核 + 决策工作台

- 日期：2026-07-19
- 配套架构规格：[2026-07-19-schonavi-architecture-and-design-system.md](2026-07-19-schonavi-architecture-and-design-system.md)
- 状态：产品方向与目标技术基线已锁定，待拆分 implementation plan
- 范围：确定 SchoNavi 长期产品方向、与豆包/小红书的差异化、目标信息架构、可信数据闭环和分阶段验证路径。
- 非范围：本文不是单 feature 实现 spec；各阶段通过验证门槛后，再分别产出 implementation plan。

## 一句话结论

SchoNavi 不做“另一个聊天机器人”，也不做“小红书式经验信息流”。产品采用**对话作为决策入口、作战资产作为留存主体、已验证案例作为质量飞轮**的综合形态。

> 小红书让用户看到别人怎么做，豆包告诉用户可以怎么做；SchoNavi 记住用户正在做什么，用可核验的竞赛与导师信息，把选择变成会随截止日期和执行结果持续更新的行动计划。

最终目标是 4 个一级入口：决策、作战室、案例、我。但四 tab 是经使用数据验证后的**目标信息架构**，不是重构起点。差异化闭环未被验证前，不先建设三个空占位 tab。

## 目标技术基线与仓库边界

SchoNavi 作为全新项目在一个 polyglot monorepo 中开发。本文提供完整目标状态，不设兼容层。技术决策固定为：

| 层 | 选型 | 职责边界 |
|---|---|---|
| Android App | Kotlin、Jetpack Compose、Material 3 | 主产品客户端，优先承载决策、作战资产、提醒与移动端深链 |
| Web | Next.js App Router、React、TypeScript | 桌面/浏览器客户端；分阶段补齐高价值流程，不要求首期与 Android 页面完全对称 |
| 主后端 | TypeScript、Node.js 当前 LTS、NestJS、Fastify Adapter | 独立 API 服务，采用模块化单体；承载身份、事实、决策、对话、资产、案例与治理 |
| 数据 | PostgreSQL | 主业务与审计数据；缓存、队列等基础设施只有在出现经验证的需求后再引入 |
| 跨端契约 | OpenAPI + JSON REST + SSE | OpenAPI 是 Android、Web、后端之间的唯一公开业务契约；SSE 用于对话增量事件 |

明确不做 iOS 和 Flutter 客户端。主后端不用 Python 或 Go，也不把核心业务 API 放进 Next.js Route Handlers；Next.js 只允许保留 Web 专属的薄 BFF、认证回调或页面组合逻辑，不能形成第二套业务后端。

爬虫、批量采集和外部数据清洗不在本 spec 和首期 monorepo 骨架范围内。未来如需爬虫，作为独立服务通过版本化的数据摄入契约向主后端提交候选事实；其语言、调度和部署单独立项，不能直接依赖主 API 的内部模块或绕过事实审核写入产品可见数据。

目标仓库逻辑边界如下，目录名可在初始化 implementation plan 中微调，但职责不得混淆：

```text
apps/
  android/              # Kotlin + Compose
  web/                  # Next.js + TypeScript
services/
  api/                  # NestJS + Fastify 模块化单体
packages/
  api-contract/         # OpenAPI、SSE 事件 schema、契约测试夹具
  design-tokens/        # 跨端语义 token 源，不存平台组件实现
  web-api-client/       # 由 OpenAPI 生成，禁止手写复制 DTO
  test-fixtures/        # 脱敏、确定性的跨端契约样例
infra/                  # 本地与部署基础设施；不包含爬虫占位服务
```

Android 的生成客户端留在 Gradle 模块内或生成目录中，不通过 TypeScript package 共享运行时代码。所谓“共享类型”是共享 OpenAPI/schema，再分别生成 Kotlin 与 TypeScript 类型。

TypeScript workspace 使用 pnpm 管理 `apps/web`、`services/api` 和 `packages/*`；Android 保持独立 Gradle wrapper 与版本目录。根级 CI 可以编排两套构建，但任何一端都不能依赖另一端的未发布构建产物。首期不因“monorepo”默认引入 Turborepo、Nx 或微服务框架。

## 背景与方向决策

大学生在竞赛和导师选择中面临的主要问题不是缺少通用回答，而是信息分散、时效难判断、建议脱离个人约束，以及一次咨询无法持续转化为行动。因此产品从零建立以下能力：导师推荐、竞赛推荐、追问、详情、匹配、对比、收藏、备赛计划、计划助手与受控案例。

长期产品化的主要挑战是：

1. 用户是否愿意把一次 AI 回答保存为需要持续回访的任务资产。
2. 推荐依据是否足够新、足够可信，能支撑升学和竞赛决策。
3. 产品是否能获得真实执行与结果数据，而不是循环使用 AI 自己生成的内容。
4. 小团队能否先验证闭环，再承担导航、账号、内容治理和后端扩展成本。

因此采用“对话内核 + 决策工作台”，而不是在“纯聊天”和“综合社区”之间二选一。

## 首批用户与核心任务

### 首批滩头用户

首个验证版本聚焦：

> 第一次或第二次参加大学生竞赛、尚未确定赛事与准备节奏、需要在本学期形成可执行计划的大一至大三学生。

选择竞赛场景作为首个闭环，原因是它天然具有截止日期、任务进度、结果回收和再次参赛周期，更容易验证“决策资产是否带来回访”。

导师选择继续保留在产品中，但作为第二条业务链路，不与竞赛闭环共享未经验证的用户、频率和留存假设。只有当通用资产模型被证明适用时，才将导师推荐、对比和套磁完整迁入作战室。

### 核心用户任务

首批用户需要完成的不是“问一个问题”，而是：

1. 根据个人背景和时间约束筛选一个适合参加的竞赛。
2. 看懂推荐依据、官方来源、关键日期和不确定项。
3. 把选择变成带里程碑和下一步行动的计划。
4. 在执行中更新进度，并根据延期、规则变化或能力变化调整计划。
5. 完赛后留下结果和复盘，在用户授权后形成可复用案例。

## 竞品基线与差异化边界

竞品能力会持续变化，本 spec 不再用“结构性做不到”作为论据，也不依赖未经注明时间和来源的 MAU 数字。以下判断只用于界定 SchoNavi 的产品合同，而不是断言竞品永远不会进入该领域。

- 豆包已经覆盖联网问答、办公任务、专家模式、定时任务和多类结构化产物。参考：[豆包 App Store 产品说明](https://apps.apple.com/cn/app/%E8%B1%86%E5%8C%85-%E9%9A%8F%E6%97%B6%E5%B8%AE%E5%BF%99%E7%9A%84-ai-%E5%8A%A9%E6%89%8B/id6459478672)。
- 小红书的优势不只是内容流，也包括强搜索意图、真实经验和社区互动；其商业产品也明确覆盖搜索信息流。参考：[小红书商业产品](https://e.xiaohongshu.com/product)。

| 维度 | 豆包的默认产品合同 | 小红书的默认产品合同 | SchoNavi 要建立的产品合同 |
|---|---|---|---|
| 用户起点 | 提问或交付通用任务 | 搜索、浏览、比较他人经验 | 提交带背景、约束和截止日期的学术/竞赛决策 |
| 事实依据 | 广泛联网信息，领域深度依任务而定 | 社区内容丰富，但时效与准确性不统一 | 关键结论必须关联官方来源、核验时间和适用范围 |
| 个性化 | 可使用对话上下文和通用记忆 | 依赖搜索词与推荐画像 | 使用用户确认的学术档案、当前计划和真实进度 |
| 产物 | 回答、文档、任务等通用产物 | 笔记、收藏、评论和搜索结果 | 带状态、期限、依据、下一步和变更记录的作战资产 |
| 持续性 | 通用对话或任务连续性 | 内容消费和社区关系连续性 | 围绕同一决策从选择、执行到结果持续更新 |
| 反馈数据 | 通用满意度和使用行为 | 浏览、互动和创作行为 | 建议采纳、任务完成、偏差、结果和复盘 |

SchoNavi 的差异化不是“聊天 + 收藏 + 社区”三个功能相加，而是以下不可拆分的链路：

```
可核验事实 → 个性化决策 → 可执行资产 → 进度与结果 → 已验证案例
     ↑                                                   │
     └────────────── 案例与结果改善下一次决策 ────────────┘
```

只完成其中一段不能形成差异化：没有事实层，资产会持久化错误；没有执行状态，资产只是收藏夹；没有结果回收，案例只是 AI 内容循环。

## 四层产品能力与优先级

### 1. 最小可信事实层：所有决策的地基

不建设追求完备的独立“竞赛百科”或“教授知识图谱”，但任何进入推荐、计划和案例的关键事实必须至少包含：

- 官方或明确标注类型的来源 URL。
- 来源名称与最后核验时间。
- 报名、提交、比赛等关键日期及其时区。
- 规则版本、适用赛区/组别和适用年份。
- `verified`、`stale`、`conflicting`、`unknown` 等状态。
- 事实变化时可能受影响的推荐或作战资产引用。

界面必须让用户看见“为什么这样推荐”“信息何时核验”“哪些信息仍不确定”，不能只在后台保存来源。

### 2. 个性化决策：结合已确认背景和当前状态

匹配输入由三部分组成：

- 用户主动填写并确认的基础背景、能力、方向和偏好。
- 用户已确认的 AI 档案建议。
- 正在执行的计划、可投入时间和既往结果。

LLM 从对话中提取的新信号只能先进入“待确认建议”，不得静默写入正式档案。用户可以接受、修改、忽略或长期关闭该类建议。

### 3. 对话产物资产化：从回答变成进行中的工作

资产不是静态收藏。每项资产至少具有：

- 类型、标题和来源业务对象。
- 状态、下一步行动、截止日期和进度。
- 创建依据、来源快照与最后更新时间。
- 用户修改记录与 AI 建议记录。
- 重新核验、继续对话、迭代和归档入口。

作战室可以用统一的 `WorkspaceItemSummary` 聚合展示不同资产，但不预设用一个 `AssetRepository` 统一所有存储。备赛计划、收藏、对比、邮件等继续保留各自领域实体、repository 和数据所有权边界。

### 4. 已验证案例：来自执行结果的数据飞轮

案例必须区分来源和成熟度：

| 类型 | 含义 | 可否作为匹配依据 |
|---|---|---|
| AI 示范模板 | 为解释产品结构而生成，无真实执行者 | 否，只能用于冷启动展示 |
| 用户计划 | 用户保存但尚未开始或尚无进度 | 否，只能作为个人资产 |
| 执行中案例 | 有真实进度、偏差和调整记录 | 可作为弱参考，必须标注状态 |
| 已完成案例 | 有完成情况、结果和复盘 | 可以，权重取决于完整度与新鲜度 |
| 已核验案例 | 关键结果或事实经过证据/人工核验 | 可以，作为最高可信等级 |

案例至少记录：原始目标、脱敏背景、计划、实际执行差异、完成情况、结果、建议采纳情况、复盘、来源状态和核验等级。

AI 可以帮助结构化、摘要和脱敏，但不能把 AI 生成内容伪装成真人经验，也不能让 AI 示范模板参与匹配质量计算。

## 案例而非传统社区

“案例”是结构化决策参考库，不是小红书式信息流，也不承担关系社区职责。

不做：关注关系、私信、泛评论、热点信息流、创作者排行、问答互助和组队撮合。

案例列表优先服务有明确意图的筛选与复用：

- 按年级、专业方向、竞赛类型、投入时间、案例状态和核验等级筛选。
- 展示“为什么与我相似”，而不是只显示抽象相似度分数。
- 默认展示与当前决策相关的少量案例，不制造无限滚动消费。
- 支持“一键复用为我的计划草稿”，复制后必须重新核验日期和规则。

内容冷启动可以使用少量人工审核的 AI 示范模板，但必须永久标注“AI 示范”，与用户执行案例分区展示，并且不进入相似案例排序训练或质量评估。

## 目标信息架构

当薄闭环和案例价值通过后述指标验证后，目标形态为：

```
底部导航（4 tab，默认=决策）
├─ 决策    对话入口、最近决策、导师/竞赛任务、基于资产继续
├─ 作战室  进行中的计划、候选、对比、邮件与归档资产
├─ 案例    结构化执行案例、筛选、详情与复用
└─ 我      档案建议、账号、案例管理、隐私与设置
```

### 决策 tab

- 保留导师/竞赛双入口、自然语言输入、对话式推荐、推荐卡、追问和 fork 能力。
- 首页优先呈现当前最需要处理的决策和下一截止日期，而不是堆叠通用 prompt。
- 新对话可以显式选择一个或多个已有资产作为上下文，并在发送前展示将引用的内容。
- 推荐结果展示官方来源、核验时间、关键期限、不确定项和“为何适合我”。
- 相似案例只作为可解释的参考，不直接替代官方事实和用户约束。
- 历史入口明确归入决策 tab 的“最近决策/全部历史”，不能在移除抽屉时丢失。
- 对话提取的档案信号以可撤销的待确认卡呈现，确认后才写入档案。

### 作战室 tab

作战室按用户任务状态组织，而不是按技术实体堆放：

1. 需要处理：临近截止、信息过期、AI 建议待确认、任务逾期。
2. 进行中：当前竞赛计划、导师候选和正在迭代的材料。
3. 已保存：推荐结果、对比报告和未启动草稿。
4. 已归档：完成、放弃或失效的资产及复盘。

| 资产 | 作战室能力 |
|---|---|
| 备赛计划 | 进度、下一任务、提醒、规则变化重算、完成与复盘 |
| 导师/竞赛候选 | 保存理由、来源快照、状态变化、继续比较或转为计划 |
| 对比报告 | 可回访、基于新事实重新比较、保留版本差异 |
| 套磁邮件 | 草稿、用户修改、发送状态、回复后的下一轮迭代 |

任何 AI 迭代都必须显示加载、成功、失败和可重试状态；异步处理中禁止重复提交。删除、覆盖和公开分享前必须确认，并尽量提供撤销。

### 案例 tab

- 默认入口是与用户当前目标相关的案例，而不是全站热门内容。
- 卡片明确展示来源类型、执行状态、核验等级、适用年份和最后更新时间。
- 详情页同时展示“计划是什么”和“实际发生了什么”。
- 用户可以复用案例，但复用后得到的是待核验草稿，不能原样复制过期日期。
- 用户可以报告过期、失实、疑似可识别信息或不当内容。

案例 tab 的一级导航资格需要通过验证门槛。验证前，案例以决策结果中的相关模块和二级页面存在，不提前占用底部 tab。

### 我 tab

- 账号与游客状态。
- 主动填写的档案。
- AI 提取的待确认档案建议，以及已接受/已拒绝记录。
- 我的案例：草稿、审核中、已发布、已撤回。
- 授权管理：哪些资产可以被用于生成案例或改善匹配。
- 数据导出、删除账号、隐私协议、主题和其他设置。

## 导航与跨页面体验约束

- 底部导航使用路由壳实现，每个 tab 保留各自导航栈和滚动/输入状态。
- Android 返回键优先退出当前 tab 的详情层级；位于 tab 根页面时再按产品约定退出应用。
- 深链可以直接进入资产或案例详情，返回后落到正确 tab，而不是无条件返回首页。
- 对话或 AI 任务生成中切换 tab 不应静默丢失任务；若离开会中断，必须提前说明。
- 所有列表和异步页面必须定义 loading、empty、error、stale 和 retry 状态，异步内容预留空间避免跳动。
- 触控目标不小于 44×44 逻辑像素；状态不能只依赖颜色表达；图标按钮必须有语义标签。
- 正文保持可读字号和对比度；动效遵循系统减少动态效果设置。

## 身份、隐私与信任

### 身份前置关系

- 游客可以完成首次决策，并在本机保存由客户端持有的备赛计划。
- 公开分享案例、跨设备同步、管理已发布案例和长期云端档案需要稳定账号。
- 不强制用户在首次提问前注册；在出现明确跨端或公开分享价值时再解释并请求登录。

账号体系与云端同步由同一 monorepo 的 `services/api` 提供，但仍需独立的身份与数据治理 implementation plan；产品 spec 必须定义游客升级、资产认领、跨端同步和删除体验。

### 档案推断

流程固定为：

```
对话提取 → 生成待确认建议 → 用户接受/修改/拒绝 → 写入正式档案
```

- 拒绝建议不会删除用户原始对话，但不得继续作为已确认档案使用。
- 用户可以关闭后续档案建议。
- 每个字段显示来源、更新时间和置信信息；置信度不能替代用户确认。

### 案例分享与脱敏

流程固定为：

```
选择个人资产 → 生成本地/服务端案例草稿 → AI 辅助脱敏
→ 高亮删除与泛化内容 → 用户逐项确认 → 发布
```

- 学校、专业、年级、地区、时间、研究方向的组合可能间接识别个人，脱敏检查不能只匹配姓名和联系方式。
- 发布前展示最终公开版本和仍可能形成识别风险的字段。
- 用户拥有编辑、撤回和删除权；删除后不得继续向新请求返回该案例。
- 涉及导师评价、学校评价和比赛争议内容时，需要报告与审核入口。
- 发布状态、失败原因、审核结果和删除结果必须明确反馈，不能静默完成。

## 成功指标与验证门槛

### 北极星指标

**每周发生至少一次用户确认进度、完成任务或重新规划的活跃作战资产数。**

该指标衡量用户是否把 SchoNavi 当作持续决策与执行工具，而不是一次性聊天入口。

### 核心指标

| 层级 | 指标 | 要回答的问题 |
|---|---|---|
| 激活 | 首次会话形成资产率、首个下一步确认率 | 回答是否真的转化成行动 |
| 留存 | D7 同资产回访率、周进度更新率 | 用户是否围绕同一目标回来 |
| 执行 | 任务完成率、逾期后重新规划率、计划归档率 | 资产是否帮助执行而非只被收藏 |
| 信任 | 官方来源覆盖率、事实过期率、用户纠错率、建议撤回率 | 推荐是否可信且可控 |
| 案例 | 完成案例授权分享率、案例复用率、复用后资产形成提升 | 案例是否真实改善决策 |

### 初始验证门槛

以下为小规模试点假设，获得首轮基线后允许在新 spec 中调整：

- 至少 12 名目标用户完成可用性测试，其中 9 名无需指导完成“理解依据→保存计划→确认下一步”。
- 至少 30 名试点用户中，首次会话形成资产率达到 40%。
- 形成资产的用户 D7 同资产回访率达到 20%。
- 70% 的测试用户能正确识别来源状态、AI 示范和真实执行案例的区别。
- 在案例成为底部一级 tab 前，必须已有稳定供给的真实执行案例，并证明相关案例模块能提升资产形成率；不能以 AI 示范模板数量替代。

## 跨端与 API 契约边界

### 工程纪律

- 新 monorepo 在 `packages/api-contract` 保存经评审的 OpenAPI 与 SSE 事件 schema；Android 和 Web 客户端从契约生成类型与调用层。禁止复制 DTO、以共享 TypeScript 类型替代线协议，或为 Android 引入 tRPC 专属契约。
- 主 API 使用 HTTP 状态码表达传输结果，错误响应采用统一的结构化 problem 形状，至少包含稳定业务错误码、用户安全文案、`request_id` 和可选字段级错误。
- 后端所有数据只经公开 API 访问；客户端允许缓存用于性能和短暂离线展示，但缓存必须带新鲜度，不能成为生产数据源或在请求失败时伪装成最新事实。
- 测试和 Compose/Storybook 预览通过接口 fake、MockWebServer/MSW 或固定契约 fixture 注入数据，不增加生产运行时 `mock|http` 开关。
- 事实来源、授权、删除、幂等、并发和安全约束必须在契约评审中定义，不能只按页面形状倒推接口。

### 客户端与服务端实现边界

- Android 使用 Compose + Material 3、ViewModel + Coroutines/StateFlow、Navigation Compose 和依赖注入；网络层基于 OkHttp 及生成的 Kotlin 客户端，结构化本地数据使用 Room，偏好使用 DataStore，凭证由 Android Keystore 支撑，可靠后台任务使用 WorkManager。具体库版本在仓库初始化时锁定。
- Web 使用 Next.js App Router + TypeScript；默认使用 Server Components，只有交互状态、浏览器能力和流式消费需要 Client Components。Web 通过生成的 TypeScript 客户端访问 `services/api`。
- 后端使用 NestJS + Fastify Adapter 的模块化单体。Controller/transport DTO、application use case、domain model 和 persistence adapter 分层，领域模块之间通过公开 application port 协作，不直接跨模块访问表。
- 首期只有一个可部署主 API，不预拆微服务；Redis、消息队列和独立 worker 必须由可观测到的重试、吞吐或调度需求触发。

### 数据所有权

- 后端权威数据：账号、已确认档案、教授/竞赛事实、推荐、会话、收藏、已登录用户的作战资产、授权、公开案例、反馈和审核记录。
- 设备本地数据：游客草稿、未发送输入、UI 偏好、通知调度状态和可丢弃缓存。
- 游客创建的计划可以先保存在本机；登录后必须由显式“认领/合并”流程迁移到账号，不能静默覆盖云端版本。
- 需要 Android 与 Web 同步的资产不能继续被定义为永久客户端自有数据。跨端写入使用 `revision`/ETag 等乐观并发控制，并定义冲突展示与重试语义。

### 最小事实字段

推荐、计划和案例响应中引用的关键事实需要提供：

```text
source_url
source_name
source_type
verified_at
applicable_period
freshness_status
conflict_note
```

具体字段命名以 `packages/api-contract` 中的 OpenAPI 为准。产品需求先在本文确定语义，再由契约定义可生成的线协议字段。

### 档案建议需求

- `POST /profile/inference-suggestions`：从指定对话轮次生成待确认建议，不直接修改正式档案。
- `GET /profile/inference-suggestions`：读取待确认建议。
- `PATCH /profile/inference-suggestions/{id}`：接受、修改或拒绝建议；接受后返回更新后的档案字段。
- 用户关闭建议、撤销已接受字段和数据删除所需契约在对应阶段补齐。

### 案例需求

- `POST /case-drafts/desensitize`：根据用户拥有的源资产生成脱敏草稿；此时不创建公开案例。
- `POST /cases`：用户确认最终公开内容后发布案例。
- `GET /cases?filters=...&cursor=...`：按背景、类型、状态、核验等级等筛选并分页。
- `GET /cases/{id}`：获取案例详情、来源状态和“为什么与我相似”的解释。
- `POST /cases/similar`：为当前决策请求少量相似案例。
- `GET /me/cases`：管理本人草稿、审核中、已发布和已撤回案例。
- `PATCH /cases/{id}`：编辑允许修改的公开内容或状态。
- `DELETE /cases/{id}`：撤回/删除本人案例。
- `POST /cases/{id}/reports`：报告失实、过期、隐私或不当内容。

上传原始资产引用、相似匹配输入、授权范围和删除语义必须在 API 契约中明确，不能只记录自由文本请求体。

## 分阶段验证与开发路径

每阶段都设置产品门槛。未通过时先修正假设，不以“代码已完成”自动进入下一阶段。

### 阶段 0：差异化原型与事实标准

- 锁定首批竞赛用户及核心任务。
- 定义最小可信事实字段、案例成熟度、档案建议确认流和关键指标埋点。
- 用可点击原型验证“查看依据→保存计划→确认下一步→回访更新”任务。
- 建立 monorepo 最小骨架、OpenAPI/SSE 契约检查和 Android/Web/后端各自的最小构建。
- 不创建案例、爬虫、消息队列或微服务占位模块。

完成判定：达到可用性测试门槛；官方来源、AI 示范、真实案例和待确认档案在视觉与文案上可被正确区分；三端最小构建和契约破坏检查可在 CI 独立通过。

### 阶段 1：Android + TypeScript API 跑通竞赛薄闭环

- 以 Android 为首个主客户端实现决策首页，把竞赛推荐保存为游客本地计划或登录用户云端候选草稿。
- 计划明确展示来源、截止日期、下一步和重新核验状态。
- 用户可以从历史或计划列表回到同一决策，并更新一次真实进度。
- `services/api` 同期只实现该黄金路径需要的模块，SSE、幂等键、`request_id`、错误 problem 和 revision 契约端到端可验证。
- 使用 repository fake、MockWebServer 和 Compose UI 测试完成定向验证；正式后端数据不增加本地 fallback。

完成判定：决策→资产→回访→进度更新的黄金路径可用，开始采集资产形成率和 D7 回访率。

### 阶段 2：作战室聚合、资产引用与 Web 薄切片

- 在薄闭环达到初始激活信号后，引入作战室页面。
- 先聚合备赛计划和竞赛候选，再按实际使用证据纳入导师候选、对比和邮件。
- 使用 `WorkspaceItemSummary` 聚合展示，不强行统一各领域 repository。
- 新对话可以显式挂载资产，生成前展示引用内容；AI 迭代保留来源快照和版本。
- Web 只实现已经在 Android 验证有价值的“查看依据→继续决策→更新资产”薄切片，复用同一 OpenAPI 和设计 token，不追求页面逐像素复制。

完成判定：不同资产可按“需要处理/进行中/已保存/已归档”查看；资产引用和迭代不破坏各领域自身行为；同一登录资产可在 Android 与 Web 间正确往返且冲突可解释。

### 阶段 3：身份与受控活档案

- 接入稳定账号及游客升级路径，处理资产归属和跨端前置条件。
- 上线“对话提取→待确认建议→用户确认→档案更新”。
- 支持建议拒绝、关闭、撤销和来源查看。

完成判定：游客首次使用不被登录阻断；公开分享和跨端能力均绑定明确身份；未经确认的推断不进入正式匹配档案。

### 阶段 4：导航壳成型

- 当决策与作战室已有真实使用数据后，引入底部导航壳。
- 初始可采用“决策/作战室/我”三 tab；案例仍作为决策中的相关模块和二级页。
- 明确安置历史、收藏、计划、档案、设置和隐私入口；核心入口不得依赖隐藏手势。
- 保留每个 tab 的导航栈、输入状态和深链语义。

完成判定：所有已上线入口可从目标导航到达；返回键、深链、生成中切 tab、loading/empty/error/stale 状态通过定向测试和真机手测。

### 阶段 5：真实案例闭环与第四 tab

- 先上线 AI 示范模板和少量人工审核的真实案例，但两者严格分区。
- 上线“资产→脱敏草稿→用户确认→发布→管理/撤回/报告”。
- 回收进度、结果与复盘，只有符合成熟度要求的案例参与相似匹配。
- 验证相关案例是否提升资产形成率和决策信任。
- 达到案例一级导航门槛后，案例升级为第四个底部 tab。

完成判定：案例来源与成熟度可解释；删除与撤回生效；AI 示范不进入质量飞轮；真实案例被证明改善至少一项核心决策指标。

## 不做的事

- 不做独立竞赛资讯流或追求完备的竞赛百科。
- 不做泛经验贴广场、关注关系、私信、泛评论、创作者排行、问答互助或组队撮合。
- 不把 AI 示范模板包装成真人案例，也不让它们参与匹配质量计算。
- 不以底部 tab 数量代表产品完整度；没有一级使用频率的功能留在二级页面。
- 不用一个通用 `AssetRepository` 覆盖生命周期和数据所有权不同的领域实体。
- 不添加生产运行时 mock 数据源或后端所有数据的本地 fallback。
- 不把 Next.js 当作第二套核心业务后端，不使用只能服务 TypeScript 客户端的私有线协议替代 OpenAPI。
- 不在首期主 API 中实现或预建爬虫；爬虫未来作为独立服务另立 spec。
- 不在产品 spec 中锁死后端表结构、匹配算法或模型实现。
- 不在事实可信度、身份和撤回机制未完成前开放公开案例分享。

## 本 spec 的完成判定

本 spec 完成不等于全量产品已经获准一次性实施。完成判定为：

1. 用户审阅并确认首批竞赛用户、差异化链路和目标信息架构。
2. 阶段 0 的事实字段、案例等级、原型和指标口径进入对应 implementation plan。
3. 后续阶段严格按验证门槛分别立项，不跨阶段预建空导航、公开社区或未经确认的档案推断。
